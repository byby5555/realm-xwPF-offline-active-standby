# 质量检查系统（线路劣化观测 → 建议切换 → 自动切换）

> 状态：**设计已定，第一期（只观测）待实现**。
> 本文档描述「按线路质量判断是否该切换」的设计。判定口径来自用户裁定（2026-10-24）：
> **不是绝对阈值，而是「相对基线的劣化增量」**，且必须**持续一段时间**才成立。
> 示例：平时 100ms，突然涨到 150ms（增量 50ms > 30ms 阈值）并持续 10 秒 ⇒ 判定劣化。

---

## 1. 为什么是「相对增量」而不是绝对值

绝对阈值（如「时延 > 30ms」）对转发链路没有意义：同城机房 2ms 就是优秀，跨洲 180ms 也可能正常。
用户真正要抓的是**劣化**——「本来 100ms，突然变 150ms」。

⇒ 判定量 = `当前值 − 基线值`（基线 = 近期正常水平的滑动平均）。

---

## 2. 参数（每条规则可配，缺省即关闭）

| 参数 | 默认 | 含义 |
|---|---|---|
| `QUALITY_LATENCY_DELTA_MS` | `30` | 时延劣化阈值：相对基线的增量（毫秒） |
| `QUALITY_LATENCY_HOLD_SECONDS` | `10` | 时延劣化需持续多久才成立 |
| `QUALITY_LOSS_DELTA_PERCENT` | `10` | 丢包率劣化阈值：相对基线的增量（百分点） |
| `QUALITY_LOSS_HOLD_SECONDS` | `10` | 丢包率劣化需持续多久才成立 |
| `QUALITY_BASELINE_WINDOW` | `10` | 基线窗口：取最近多少轮算平均 |
| `QUALITY_SWITCH_ENABLED` | `false` | **切换层总开关**（第一期恒为 false） |

判定规则：**参数缺省或为 0 ⇒ 该项不参与判定**（不写 = 关）。

## 3. 数据来源与计算

### 3.1 时延
- **现成**：状态行里已有 `LATENCY_MS`（本轮）与 `LATENCY_HISTORY`（逗号分隔的历史窗口），
  读侧 `latency_avg_ms` / `format_latency_display` 已能算均值。
- **基线** = 最近 `QUALITY_BASELINE_WINDOW` 轮的 `LATENCY_HISTORY` 平均值。
  ⚠️ 基线**必须排除当前这一轮**，否则增量会被自己稀释。
- **劣化** = `本轮时延 − 基线 > QUALITY_LATENCY_DELTA_MS`。

### 3.2 丢包率
- **现状不够用**：状态行里的 `FAIL_COUNT` / `SUCCESS_COUNT` 是**连续**计数（成功一次就清零），
  不是窗口计数 ⇒ 算不出丢包率。
- **需要新增**：一个**窗口计数**（最近 N 轮里失败了几轮 / 共几轮）。
- **劣化** = `本轮窗口丢包率 − 基线窗口丢包率 > QUALITY_LOSS_DELTA_PERCENT`（百分点）。

### 3.3 持续时间
- 探测轮间隔 = `HEALTH_CHECK_INTERVAL`（默认 4s）。
- 「持续 N 秒」⇒ 需要**连续 `ceil(N / 轮间隔)` 轮**都判定为劣化。
  例：N=10s、轮间隔 4s ⇒ 连续 3 轮劣化才成立。
- 需要跨轮保存两个量：**连续劣化轮数** + **劣化起始时间戳**。

## 4. 状态文件扩展（兼容性硬要求）

现状状态行格式（9 字段）：

```
RULE_ID|TARGET|STATUS|FAIL_COUNT|SUCCESS_COUNT|LAST_CHECK|FAILURE_START_TIME|LATENCY_MS|LATENCY_HISTORY
```

新增字段**一律追加在尾部**，不改动前 9 个字段的位置：

```
...|LATENCY_MS|LATENCY_HISTORY|QUALITY_STATE|LATENCY_BASELINE_MS|LOSS_WINDOW|LOSS_BASELINE_PERCENT|DEGRADE_SINCE
```

| 字段 | 含义 |
|---|---|
| `QUALITY_STATE` | `ok` / `degraded` / 空（未启用质量判定） |
| `LATENCY_BASELINE_MS` | 本轮算出的时延基线 |
| `LOSS_WINDOW` | `失败轮数/总轮数`（窗口丢包率） |
| `LOSS_BASELINE_PERCENT` | 窗口丢包率基线 |
| `DEGRADE_SINCE` | 本轮劣化起始时间戳（未劣化则空） |

**兼容性两条硬要求**：
1. **旧格式行（只有 9 个字段）必须仍能读出来** —— 缺的质量字段按「没有质量数据」处理，
   **不能当成「一切正常」**（否则老文件会被误判成健康）。
2. 状态文件仍**每轮原子重建**（先写临时文件再 `mv`），并按 **(RULE_ID, 目标地址) 组合键**继承跨轮计数
   （两者都要对上 —— 只按 RULE_ID 会被「规则 ID 被下一个规则复用」坑到；
   只按目标地址会在「同一后端被两条规则共用」时把状态过户给另一条规则；
   任一不同就认不出旧行 ⇒ 从零重新计数，那是最多晚几轮才切换的**安全方向**）。

## 5. 分期计划

| 期 | 内容 | 切换行为 |
|---|---|---|
| **一期（观测）** | 算基线、算增量、算持续轮数、结果落进状态文件 + 负载均衡菜单显示「已劣化 / 持续 xx s」 | **无**。硬红线：不得有任何自动切换行为变化 |
| **二期（建议切）** | 劣化持续超阈值时，菜单里把该目标标红并提示「建议切备」；**由用户点一下才切** | 人工触发 |
| **三期（自动切）** | 劣化持续超阈值 ⇒ 自动切到备；恢复阈值（连续正常 N 轮 + 冷却）后切回 | 自动 |

### 三期必须解决的两个问题（先记在这里，避免到时候才发现）
1. **与现有故障转移共用一个改写点**：现有「连接失败 ⇒ 改写 `TARGET_STATES`」和新的「质量劣化 ⇒ 改写
   `TARGET_STATES`」是两个状态机，**同时改同一个字段会互相踩**。必须收敛到单一写点 + 单一状态机。
2. **探测端自身可靠性**：主备池整块删除后，健康探测端是主备切换**唯一**的驱动。
   在探测端还没做完「装/升级重生成 + 超时预算 10s + 状态文件原子重建」之前叠第二层自动切换，
   等于给切换决策加第二个不确定源 —— 出了事分不清是探测坏了还是质量阈值误判。

## 6. 为什么不改成 tcping

- 现状探测是 **TCP 握手**（`nc -z` 优先，缺 nc 回退 bash 内置 `/dev/tcp`），**不是 tcping**。
- 理由一：精简 VPS 常常连 netcat 都没有，更没有 tcping；`/dev/tcp` 回退是「缺 nc 时不把所有目标
  误判成故障」的关键（否则永远不切换）。
- 理由二：tcping 走 ICMP，很多机房/云厂商封 ICMP —— **ping 通不代表业务端口通**。
  这里要判断的是「转发能不能走通」，TCP 握手更贴近真实。
- 丢包率若真要准，得做「N 次探测里失败 M 次」的窗口计数；ICMP 的丢包率不反映转发链路丢包。

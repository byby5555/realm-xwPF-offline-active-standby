# 测试台架说明（realm-xwPF-offline-active-standby）

> 本目录由「阿测」维护。台架版本：`v2.5.0 (frozen-base + probe-unique + M1/M2/M5/M7/M8 + commit-msg-contract + T32-form-agnostic + T43-T52-coverage + health-target-hostport)`。

## 一句话

`bash tests/run_tests.sh` —— 在**沙箱**里跑 52 条回归用例，
被测产物从**冻结点 SHA** 导出（不读工作区），只读仓库、绝不碰 `/etc`、`/usr`、`/var`。
全过退出码 0，有失败非 0。

## 跑法

```bash
bash tests/run_tests.sh                  # 全部用例（BASE_SHA 默认 = 当前 HEAD）
bash tests/run_tests.sh --only T10,T14   # 只跑指定用例
bash tests/run_tests.sh --repeat 3       # 连跑 3 轮，校验结果一致
bash tests/run_tests.sh --list           # 列出用例编号
bash tests/run_tests.sh --clean          # 跑完删掉沙箱

BASE_SHA=a9102c1 bash tests/run_tests.sh            # 指定冻结点（推荐）
bash tests/run_tests.sh --base-sha a9102c1          # 同上
```

## 一、冻结点机制（第 2 轮起）

### 为什么要有

仓库是多人并行的：Chief、小编、审稿、阿测同时在同一个工作区改东西。
第 1 轮实测出现过「**第 1 轮红、后 2 轮绿**」的假抖动 ——
根因不是代码在动，而是**跑批读到的工作区文件在跑批过程中被改写了**。
更糟的是，提交信息写着「全过」，但那「全过」引用的是另外三套脚本的 PASS 计数，不是正式门禁。

冻结点把「这次到底测了哪一份代码」**钉死**，结论不再随工作区漂移。

### 怎么用

| 场景 | 做法 |
|------|------|
| Chief 指定冻结点 | `BASE_SHA=<sha> bash tests/run_tests.sh`，报告里写明这个 SHA |
| 小编提交后回归 | 用**同一个** SHA 重跑；若 SHA 变了，旧结论作废，必须重跑 |
| 日常本地跑 | 不指定 `BASE_SHA`，默认取当前 `HEAD`（注意：此时结论只对那一刻的 HEAD 成立） |

### 三条硬规则

1. **被测产物一律从 `git show $BASE_SHA:<path>` 导出，绝不读工作区文件。**
   沙箱里产物分三层：
   - `$SBX_RAW` —— `git show` 的**原始字节**（行尾断言的权威来源）
   - `$SBX_SRC` —— 去 CR 的 **LF 副本**（静态检查用）
   - `$SBX_RUN` —— 再加**路径重定向 + root 模拟**（功能测试用）

   桩（`tests/shims/`）永远取工作区最新版 —— 台架自己不是被测对象。

2. **SHA 不存在就直接 `exit 2`，绝不静默退化成「读工作区」。**
   静默退化 = 结论不可复现 = 比报错更危险。

3. **SHA 一变，旧结论全部作废，必须重跑。**
   报告里必须写上：冻结点 SHA、冻结点标题、台架版本、产物指纹路径。

### 产物指纹

每次跑批都会在沙箱里写一份 `manifest.txt`：

```
repo        : <仓库路径>
BASE_SHA    : a9102c1
BASE_SHA 全 : a9102c1a20719cb808f11f9f5bbe94dbefceab30
BASE 标题   : <冻结点提交标题>
harness     : v2.0.0 (frozen-base)
time        : <跑批时间>
sandbox     : <沙箱路径>

--- 当前工作区 HEAD（仅供对照，不作为被测产物）---
head        : <HEAD>

--- git status --porcelain（跑批时刻的工作区状态）---
<改动清单>

--- sha256（冻结态原始 blob = 本次被测产物）---
<每个文件一行：sha256  path>
```

三份 manifest 对不上 → 被测对象变了 → 结论不可比。

### 台架自身的版本

台架改了（新增用例、修 fixture、换沙箱策略）就把 `run_tests.sh` 里的
`HARNESS_VERSION` **bump 一个号**。旧报告里带着旧台架版本的结论，参考价值要打折。

## 三、台架做了什么（以及为什么）

### 1. 冻结态导出

见上文「冻结点机制」。关键点：**静态检查也读冻结态**，不只是功能测试。
读工作区的静态检查在并行改动下同样会给出不可复现的结论。

### 2. LF 副本

仓库 `core.autocrlf=true`，Windows 工作区是 CRLF。直接 `source` 工作区副本在 Linux 语义下会出错，
所以被测产物一律先去 CR（`$SBX_SRC`），执行副本在其基础上再做路径重定向（`$SBX_RUN`）。

行尾断言一律用 `od` 数字节（`sbx_count_cr` / `sbx_count_crlf`），
**不靠 `grep`** —— MSYS 的 `grep` 对含 CR 的模式不可靠（实测 `printf 'a\r\n' | grep -c $'\r'` 返回 0）。

### 3. 路径重定向（防越界）

副本里所有系统绝对路径都被改写到沙箱目录，映射表见 `lib/sandbox.sh` 的 `SBX_PATH_MAP`：
`/etc/realm` `/etc/systemd/system` `/etc/xwpf` `/usr/local/bin` `/var/lock` `/tmp` …
跑完会做一次**越界残留扫描**，把副本里剩下的真实系统绝对路径列出来。

**当前：越界残留 0 处。**

> 第 3 轮的一次决策：`/opt/realm` 原先只剩 1 处越界残留
> （`xwFailover.sh` 的 `find_file_path` 候选数组里的 `"/opt/realm/$filename"`）。
> 它确实只是只读探测点（`[ -f "$path" ]` 判断后 echo 路径），但**没有加进只读白名单**，
> 而是**加进了路径重定向表**（`/opt/realm` → `${SBX}/opt.realm`）。
>
> 理由：`/etc/realm`、`/var/lib/realm`、`/usr/local/realm`、`/tmp` 全都已经重定向，
> 只有 `/opt/realm` 漏网。加白名单 = 把这个口子**永久豁免**，扫描器以后就抓不到同类问题了；
> 改成重定向 = 沙箱彻底密闭（连读都不会碰到真 `/opt/realm`），扫描器回到 0 处，
> 以后任何**新的**真实越界仍然会被抓到。

### 4. root 模拟

Git Bash 的 `EUID` 是 Windows uid（197610），`check_root` 会直接 `exit 1`。
沙箱副本把 `[[ $EUID -ne 0 ]]` 改成 `false`，等价于「以 root 运行」。

### 5. 外部依赖打桩

假 bin 目录放在 `PATH` 最前。`nc` 单独放一份在 `$SBX_BIN_NC`，**默认不进 PATH** ——
这样「机器上没装 nc」是默认状态，需要时用例显式加进来做对照口径。

`curl` / `wget` 桩从**离线镜像**取文件：镜像只放冻结态的内容，
所以「本地有、但没提交」的文件在镜像里是 404 —— 这正是要暴露的问题。
桩会把每次请求的 URL 记进日志，用例据此断言「下载地址是否指向本 fork」。

### 5b. jq 桩（第 7 轮新增）

本机没有 jq，而仓库里有 **119 处** jq 调用（`lib/core.sh` / `lib/rules.sh` / `lib/update.sh` /
`notifications/*` / `port-traffic-dog.sh` / `xw_realm_OCR.sh`）——
不装桩就等于「整段依赖 jq 的配置生成路径」**完全没被测过**。

`tests/shims/jq`（实现 `tests/shims/jq_impl.py`）是只覆盖仓库真实用到的过滤语法的 mini-jq。
它的三条纪律：

1. **不会就说不会** —— 不支持的过滤器 → stderr 打印「jq-stub: 桩能力不足：\<表达式\>」+ **退出码 3**，
   让调用方的兜底分支真的走到，而不是悄悄拿到空值。
2. **能力检测与数据无关** —— 先做一遍语法校验，再求值。
   否则「数据刚好没走到那个分支」时就会静默返回空值 → 看起来测过了，其实没测。
3. **拒绝「会被静默误解」的危险语法** —— 比如 `..`（jq 的递归下降），
   桩原本会把它解析成「整个对象」，**结果看着有输出但语义全错**。这类语法必须报「不会」。

输出统一为**紧凑 JSON**（`jq -c` 的形态）；真 jq 默认缩进输出，差别只在空白 →
用例断言一律按**语义**判，不按字节。

### 6. 提交信息契约（T40，第 5 轮升级为硬断言）

第 1 轮出过事故：**另三套脚本全绿、正式入口 `run_tests.sh` 16/22 红，提交信息却写「全过」**。
第 2 轮把这件事做成了跑批末尾的**打印告警** —— 告警拦不住任何人。
第 5 轮把同一套判定搬进用例 **T40**：

- 扫描最近 N 条提交信息（`COMMIT_CHECK_N`，默认 20，锚定 `BASE_SHA`）；
- 命中「声称全过」词表 → 必须同时给出 **① 唯一入口 `tests/run_tests.sh`** 与
  **② 实测口径（`BASE_SHA` / 汇总行 / 用例总数 / 退出码，任一）**；
- 缺任一 → **用例失败、门禁退出码非 0**，并打印「哪条提交 / 命中了哪个词 / 缺了什么」；
- 旧格式（①②都在、只缺 SHA）→ 容忍但记提示；
- 唯一入口当时还不存在的提交 → 自动豁免；
- 过渡白名单 `tests/commit-msg-exemptions.txt`：**≤3 条**，每条必写理由。

判定器本身也要被测：T40 内置 **6 组反例自检**（内存里造假提交信息，**不产生任何真实提交**），
3 条坏消息必须被抓、3 条好消息必须被放行。
白名单的三条硬约束（超限 / 没写理由 / SHA 解析不到）都做过负向对照 —— 破坏任一条都会判红。

细节与豁免名单见 `tests/README.md` 的「T40 的提交信息契约」。

## 四、已知环境限制

| 限制 | 影响 | 处理 |
|------|------|------|
| MSYS 的 `grep` 对含 CR 的模式不可靠 | 行尾断言不能靠 `grep -c $'\r$'` | 改用 `od` 数字节（`sbx_count_cr` / `sbx_count_crlf`） |
| MSYS 读文件是文本模式 | CRLF 脚本在本机能正常跑，Linux 上会挂 | 该失败模式列为「待真机验证」 |
| 本机 `python3` 是 WindowsApps 占位符 | 监听端口起不来 | 改用真实 `python`（3.11.15） |
| 没有 `jq` / `nc` / `systemctl` / `flock` | 依赖这些的路径需打桩 | 已打桩；`jq` 用 mini-jq 桩（第 7 轮）覆盖了仓库实际用到的过滤器；**桩不支持的语法会显式报「桩能力不足」**，不会假装测过 |
| 没有 WSL / Docker / shellcheck | 不能做真机级验证 | 全部列入「待真机验证」清单 |
| PowerShell 转义会坑 bash | `\|\|` / `\"` 被 PS 解析 | 复杂引号一律写成脚本文件再交给 bash 执行 |

## 五、退出码与证据

`0` = 全部通过；非 `0` = 有失败（`1`）。冻结点不存在时是 `2`（参数/环境错误，与「有失败」区分开）。

每条用例的 stdout / 断言记录 / 元信息都在
`$SBX_ROOT/cases/<编号>.{stdout,log,notes,fails,meta}`，跑完会打印沙箱路径。

同一产物连跑 3 次的结果向量必须一致（`--repeat 3` 会自动校验并打印）。
**只红一次先怀疑用例本身**：用第二口径交叉验证后再报缺陷。

## 六、断言纪律（写新用例时必读）

1. **负向对照**：新断言写完，往冻结态副本里注入一个坏输入，确认它**会红**。
   「怎么写都绿」的断言等于没有断言。
   T34 的负向对照做过 4 组：注入不存在的符号 → 抓；注入不存在的源文件 → 抓；
   注入越界行号 → 抓；把 `auto_enable_active_standby` 改名 → 抓（就是 D-01 那类回归）。
2. **命中数下限护栏**：像「解析 N 处引用」这种用例，正则一坏就是 0 命中 → 断言全过 → 假绿。
   另加一条「命中数 ≥ N」（N 取实测值的 ~1/2）。
3. **防空过护栏不是装饰**：T34 上线时，这条护栏真的拦住了我一次 ——
   我把「去重组数 63」和「出现次数 212」搞混，护栏直接判红，逼我把计数口径分开。
4. **断言行为，不钉实现位置**；**静态检查读冻结态**；
   **不要在文件头快照还没建好的沙箱路径**；**fixture 只参数化不裁剪键集**；
   **一条红灯要能被第二口径交叉验证**。
5. **别断言交互提示的文本，断言行为**。
   bash 的 `read -p` 只在 **stdin 是终端**时才把提示打到 stderr
   （bash 手册原文：*"The prompt is displayed only if input is coming from a terminal."*）。
   沙箱里喂管道 → 提示根本不显示 → 断言提示文本必然假红。
   正确做法：断言**行为**（答 `n` 会不会取消、回车会不会继续）。
6. **对照组要用对函数**。「进不进主备」由 `apply_port_group_weight_config` 的**权重判定**决定；
   `auto_enable_active_standby` 本身不看权重、只要被调用就切主备 ——
   拿它当「不进主备」的对照组会得到假红（这条真踩过）。
   （细则见 `tests/README.md` 的「写用例时的几条硬规矩」。）
7. **断言文件自身含被禁字符串是正常的，但统计必须排除断言自身**。
   否则改一下断言逻辑（改注释、换变量名）就自指假红 —— 红了也不代表产品坏了。
   做法：排除规则写进代码注释 + `tests/README.md`，
   再用「全树命中里落在 `tests/` 之外的条数 = 0」把排除的有效性**变成可验证的**（T02）。
8. **「打印告警」不是门禁**。会让人以为「已经检查过了」的提示，要升级成**可失败的用例**（T40）。
   判定器本身也要被测 —— 内置反例自检（内存造假输入，不产生真实提交）。
9. **豁免机制要有上限、要有理由、要有负向对照**（T40 白名单 ≤3 条、每条必写理由、SHA 可解析；
   破坏任一条 → 判红）。
10. **不变式必须覆盖所有合法形态，不能只覆盖当前形态**（第 7 轮 T32 的教训）。
    旧断言写的是「生成物里 `check_connectivity() {` 恰好 1 份」—— 这只对
    「机械抽取内嵌」这一种实现成立；将来把生成物改成「显式 source 已安装的真源」
    （依赖更少、漂移风险更低，是**产品变好**），份数变 0 → 误红。
    现在判的是「**生成物的探测逻辑与真源是否一致**」：
    形态 A（内嵌 1 份 + 逐字一致）与形态 B（不含内嵌副本但 source 真源且能解析到）都判过，
    其余（内嵌多份 / 逐字漂移 / 既不内嵌也不 source）才红。
    问自己一句：「把实现换成另一种同样正确的形态，它会不会误红？」
11. **破坏手法要按语义定位，别钉死代码文本**（第 7 轮 T51 的教训）。
    `sed 's|某个具体写法|...|'` 在实现一改（缩进/写法/收敛成单一函数）就静默失效，
    看着像生效了其实没对准。优先改**判定条件**、改**函数名**，
    或在副本**末尾追加一个同名函数覆盖**（bash 里后定义覆盖先定义，一定生效）。
    并且**先验证破坏生效**（注入点计数 == 1 / 坏值真的出现）再信它的红 ——
    「负向对照红了」先怀疑「破坏手法」，再怀疑「被测代码」。
12. **跑批期间不要改台架脚本**。bash 按字节偏移读脚本；跑批中途改文件会让它读到错位的片段
    → 尾部报莫名其妙的语法错（第 7 轮真踩过：51/51 的表格是对的，尾部却炸了）。
    改台架 → 改完**重跑**再取结论。
13. **fixture 的形态本身就是断言的一部分**（第 7 轮收尾 T52 的教训）。
    fixture 写成产品已经**不再产出**的旧形态 → 用例退化成「兼容兜底分支」，
    断言照样绿但主路径没人测。健康状态 fixture 已从裸 host 改成 `host:port`。
    反过来，**记录定位要格式无关** —— 产品改字段口径时，写死旧格式的定位会让整组用例替产品背锅。
14. **用例结果不能依赖跑批顺序**。沙箱跨用例共用；前面用例留下的规则文件
    （同 `LISTEN_PORT` 且 `FAILOVER_ENABLED=true`）会改变后面用例的判定。
    用例开头先清空自己要用到的目录；自查：「单独跑这一条，结果一样吗？」
    （第 7 轮收尾实测：只跑 T30 通过，跟着 T29 跑就红 —— 典型的顺序依赖假红。）
15. **负向对照优先用「真实的旧实现」**。人造 `sed` 破坏依赖代码写法，改一次就静默失效；
    「修复前的真实实现」能从 git 取到，复现的是**真症状**。取不到就**判红**，
    绝不静默跳过。断言方向也要想清楚：负向对照断言的是「**坏情况确实发生了**」，
    不是「坏情况没发生」—— 后者恒真，等于没断言。
16. **写「兼容」时，验收判据必须是「新旧两种输入的产出完全一致」**，不是「新格式不报错」。
    实操：造**同一逻辑场景**的两份输入（旧格式 / 新格式），跑同一函数，**比对输出**。
    ⚠️ 光看数值无法判断好坏 ——「1,0」既可能是「不切换的缺陷」，也可能是「全部目标都挂了
    → 走全挂兜底」的**正确行为**；必须同时记录场景与新旧是否一致。
    ⚠️ 观察量也要当心：剔除模式下「全挂兜底」只剩一个目标 → 不输出 `balance` 字段 →
    症状**观察不到**；这种场景要用主备模式观察。
17. **别把「设全局变量」的函数写进 `$(...)`**。命令替换会开子 shell，
    全局变量赋值随之丢失 → 后面拿到空串 → 源文件加载失败 →
    **负向对照静默返回空值**（看着像「症状没复现」，其实是根本没跑起来）。
18. **「兜底断言」挡不住「静默漂移」；解析器要认全部写法**（第 8 轮 T34 的教训）。
    旧口径的行号引用只在「文件不存在 / 行号越界」时红 → **行号漂了但仍在范围内 → 绿的**，
    而这正是 D-01 那类漂移最常见的形态。现在行号引用**硬断言为 0**。
    另一个盲区是**写法**：只认中文「的」式 → `README_EN.md` 里的
    `` `lib/core.sh`'s `REQUIRED_TOOLS` `` 完全不被检查（那一半文档等于没测）。
    加了新写法 → 一定要同时加**该写法的命中数下限护栏**（≥1），
    否则「正则扩了但其实没匹配上」是静默退化。

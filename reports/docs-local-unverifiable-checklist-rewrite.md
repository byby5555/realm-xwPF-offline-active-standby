# 本机不可验项清单（开发机 → 真机）

> 适用范围：`realm-xwPF-offline-active-standby` 的开发机（Windows + Git Bash + Python 3.11）。
> 真机：Linux VPS（生产环境是 Linux，行为与开发机在若干点上是**不一样**的）。
>
> 这份清单的用法：**每条都写清楚「本机为什么验不了」「真机怎么验」「验收判据是什么」**，
> 不写「本机无法验证」这种含糊话 —— 含糊的条目会在真机验收时被跳过，或者被临时改口径。
>
> **当前范围（2026-10-24）**：本清单**只写保留路径**（普通单端口中转 / 同端口多目标负载均衡 /
> 权重 `10,0` 主备 / 健康探测端 / 老机器残留清理）的不可验项。
> 配合 [真机验收清单](../reports/real-machine-acceptance.md) 用：**验收清单给「验什么」，
> 本清单给「哪几条本机根本造不出那个前提、必须上真机」。**

## 1. 故障检测耗时（停掉主后端后多久判出 `failed`）

| 本机不可验项 | 为什么本机不可验 | 真机验法 + 验收判据 |
|---|---|---|
| **停掉主后端后，探测端要多久才判定该目标为 `failed`**（即「故障检测耗时」） | 判定链路是 **systemd timer 拉起一次性探测脚本** + 真实 TCP 连接超时：① 真实 timer 的调度间隔受机器负载、脚本自身执行耗时影响；② 失败判定要等**单次探测的超时预算耗尽**才算数。本机**没有 systemd**（Windows + Git Bash），且 Windows 的 socket 超时语义与 Linux 不同 ⇒ 本机测出来的间隔**不可外推**。 | 真机上：① 停掉主后端，记下停的时刻；② `journalctl -u realm-health-check.service --no-pager -o short-iso \| grep -E '\[FAILURE\]'` 记下打出 `[FAILURE]` 判定的时刻 → **判据**：两个时刻之差 = **实测故障检测耗时**（参考实测 **30 秒**：kill 主后端 epoch `1792850569` → `[FAILURE]` epoch `1792850599`）；③ 顺带量探测间隔：`journalctl -u realm-health-check.service --no-pager -o short-iso \| grep -E '\[FAILURE\]\|\[RECOVERY\]\|\[CONFIG\]'` 看相邻两轮探测的间隔 ⇒ 参考实测 **4 / 6 / 9 / 10 / 11 / 12 / 18 / 30 秒**（**标称是 4 秒**）。<br>⚠️ **判据不是「必须 30 秒」**：**8–10 秒 → 30 秒（慢 3–4 倍）是产品事实、不是回归**（已删除的守护进程路径是 8–10 秒切走；权重路径的间隔不固定 + 超时预算从 3 秒抬到 10 秒）。**上限 > 60 秒** 才需要排查（探测卡死 / timer 没被调度 / 生成物是旧的）。<br>⚠️ **⚠️ 实测值带前提，必须连同前提一起记**：这个 **30 秒**是在**探测超时预算仍为 3 秒**的口径下测出来的；产品正把新建规则的预算从 3 秒抬到 10 秒 ⇒ **失败判定会更慢** ⇒ **30 秒在新代码下可能不再成立**。⇒ **记录实测值时必须一并记下当时的 `CONNECTION_TIMEOUT`**，且**不得拿 30 秒当判据**。 |

## 2. 回切间隔（主后端恢复后多久翻回主）

| 本机不可验项 | 为什么本机不可验 | 真机验法 + 验收判据 |
|---|---|---|
| **主后端恢复可用后，权重要多久才翻回主**。⚠️ 冷却期 `RECOVERY_COOLDOWN` 是从**故障起始**算起，**不是**从「恢复」算起 —— 故障持续得越久，恢复后等得越短 | 跨轮判定依赖 **真实 timer 跨轮推进** + **跨轮时间戳连续性**：`failure_start_time` 记在状态文件里，下一轮读回来算差值。本机没有 systemd timer，也没有跨轮持久化的状态文件 ⇒ **本机跑不出这个时间差**（本机只能跑单轮，看不到「跨轮 + 冷却」的组合）。 | 真机上：① 制造主故障，等到判定 `failed`（记下 `[FAILURE]` 时刻 = **故障起始**）；② 恢复主后端，记下恢复时刻；③ 记下 `[RECOVERY]` 判定出现、以及 `config.json` 里权重翻回主（主位 = 1、备位 = 0）的时刻 → **判据**：<br>· **回切发生在「故障起始 + `RECOVERY_COOLDOWN`(120) 秒」之后**（硬判据）；<br>· **恢复后立刻读，权重仍在备上（主位 = 0、备位 = 1）**（硬判据，与探测间隔无关）；<br>· 实测值 = 恢复 → `[RECOVERY]` 的间隔（参考实测 **119 秒**：主后端恢复可用 epoch `1792850599` → `[RECOVERY]` epoch `1792850718`；同一轮实测回切后 `balance` = `"roundrobin: 1, 0"`、**实连 3 次全部落回主** `127.0.0.3:19081`）。<br>⚠️ **不要把「必须是 119 秒」当判据**：故障若持续**超过** 120 秒才恢复，恢复后的等待会显著变短（下界 = 2 个探测周期）。 |

## 3. 探测准入三条件（不满足 ⇒ 切换完全不工作且**完全静默**）

| 本机不可验项 | 为什么本机不可验 | 真机验法 + 验收判据 |
|---|---|---|
| 承载对外端口的规则**必须**同时满足 `RULE_ROLE=1` + `ENABLED=true` + `FAILOVER_ENABLED=true`，探测端才会探它；**缺一条 ⇒ 该规则从不被探 ⇒ 切换完全不工作、且日志里连一句失败都没有** | 准入判定发生在**真机生成物** `health_check.sh` 里（由真源在装/升级时生成到机器上），依赖真实的**规则集 + 规则文件格式 + timer 调度**。本机没有真规则集也没有 timer ⇒ **本机造不出「规则存在但从不被探」这个状态**（本机上规则文件是现造的，天然满足条件）。 | 真机上：① `for f in /etc/realm/rules/rule-*.conf; do echo "== $f"; grep -E '^(RULE_ROLE\|ENABLED\|FAILOVER_ENABLED\|LISTEN_PORT\|REMOTE_HOST)=' "$f"; done` → **判据**：**承载对外端口的那条规则三条全对**（`RULE_ROLE=1` / `ENABLED=true` / `FAILOVER_ENABLED=true`）；② **反例必须判 FAIL**：`RULE_ROLE=2`（服务端 / 出口规则）、或 `ENABLED=false`、或 `FAILOVER_ENABLED=false` —— 任一命中 ⇒ 该规则**不参与探测**；③ 杀掉主后端后 → **判据**：状态文件里**该目标的行**出现并转 `failed`；**若压根没有这行 ⇒ 是准入不满足**，不是「切换慢」。<br>⚠️ 真机踩过的坑：原来那两条规则是 `RULE_ROLE=2` + `FAILOVER_ENABLED=false` ⇒ **从来没被探过** ⇒ 当时「主备能切」**完全靠被删的守护进程自己那套探测**；守护一删，切换立刻失效而**没有任何报错**。 |

## 4. `balance` 字段格式 —— 写错会让 **realm 整个 panic（全站转发断）**

| 本机不可验项 | 为什么本机不可验 | 真机验法 + 验收判据 |
|---|---|---|
| `config.json` 里每个 endpoint 的 `balance` 必须是 **`$strategy: $w1, $w2`**（**必带 `: ` 与权重、权重个数 == 目标数**）；`remote` 必须是 **string**、`extra_remotes` 必须是 **数组** —— 写成**数组 remote** 或**不带权重** ⇒ **realm 直接 panic** ⇒ **不是只断那一个 endpoint，是所有 endpoint 的转发全断** | panic 发生在 **realm 自己的二进制里**（realm 2.9.6 内 `realm_lb-0.1.1` 的 `balancer.rs`）。本机**没有 realm** ⇒ **本机跑不出这个崩溃**；而且这是**全站级**故障（所有 endpoint 一起断），本机也没有第二组 endpoint 可供对照。 | 真机上：① `jq -r '.endpoints[] \| [(.listen), (.remote\|type), ((.extra_remotes//[])\|length), (.balance//"NONE")] \| @tsv' /etc/realm/config.json` → **判据**：逐 endpoint 满足 —— `remote` 类型是 **string**；`extra_remotes` 类型是 **array**；`balance` **含 `: ` 且后面有权重**；**权重个数 == 目标数**（`remote` 1 个 + `extra_remotes` 元素数）；单目标时**不应有** `balance` 字段；② `systemctl is-active realm` → **判据** = **`active`**（**红线**：不能只看「配置生成成功」就算过）；③ `journalctl -u realm -n 50 \| grep -iE 'panic\|panicked'` → **判据**：**无 panic**；④ **实连一次**确认转发真通（正确测法见验收清单 A-13.1 判据 5：**后端回一行标识、客户端读那一行**，不能用「TCP 连得上」当通过）。<br>⚠️ **改 `config.json` 前先 `cp -a` 备份** —— 一次手滑就能把整台机器的转发打掉。<br>⚠️ **覆盖缺口**：已实测的**只有**「`remote` 为 string + `extra_remotes` 为数组 + `balance` 带权重」这一组；**权重 0 与 `iphash` 策略的组合尚未实测** ⇒ **不要**把它写成已验，遇到时**登记为「未覆盖」**。 |

## 5. 切换会重启 realm ⇒ 切换瞬间有几秒转发中断

| 本机不可验项 | 为什么本机不可验 | 真机验法 + 验收判据 |
|---|---|---|
| 权重翻转要**重启 realm 服务**才能生效（探测脚本调 `pf --restart-service`）⇒ **切换瞬间有几秒转发中断** —— 这是**机制固有代价、不是缺陷**，但必须写明，否则会被当成「切换把流量打死了」 | 依赖 **真实 systemd 的服务重启耗时**（realm 停止 → 读新 `config.json` → 启动 → 监听端口就绪）。本机没有 systemd 也没有 realm ⇒ **本机测不出这个窗口有多长**。 | 真机上：① 停掉主后端，等 `[CONFIG]` 打出 → **立刻**连续发请求，逐笔记录成败与耗时 → **判据**：能观察到一段**明确的失败窗口**（= 切换瞬间的转发中断），窗口长度 ≈ realm 重启耗时；② 窗口结束后 → **判据**：请求恢复成功，且**读回的后端标识 = 备后端**；③ `journalctl -u realm -o short-iso -n 50` 里能看到 realm 的 stop / start 时间戳 ⇒ 用来对上中断窗口。<br>⚠️ **这一条是「预期现象」不是缺陷** ⇒ 验收时**不要**因为切换瞬间有中断就判 FAIL；**但必须把它写进验收记录**（中断窗口 ≈ 几秒），因为它决定**客户端要能容忍多长的不可用窗口**。 |

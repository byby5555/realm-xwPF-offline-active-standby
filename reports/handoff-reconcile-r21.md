## 三、★ 为什么第 21 轮那批四件套不可引用（引用纪律第 ② 样 + 第 ⑥ 样的实战）

### 3.1 第 ② 样：锚点 SHA 已悬空（**致命的这一条**）

```
git cat-file -t ddfb492        → commit          （对象还在）
git branch -a --contains ddfb492 → （空）          （不在任何分支上 ⇒ 悬空）
```

⇒ **对象存在 ≠ 可引用**：它只剩 reflog 保命，任何一次 gc 就消失 ⇒ 引用一个会消失的对象，等于没有引用。

⇒ **内容指纹（rebase 只换基线、内容不变 ⇒ 结论可平移）**：

| 文件 | `ddfb492` 的 blob | 现存等价树 |
|---|---|---|
| `tests/run_tests.sh` | `4dce149450a7151f4b9bf80eb1d5e4778219ab04` | 与 Chief 分支 tip 的该文件**同 blob** |
| `tests/TEST-HARNESS.md` | `57b394e644084c7ee6fe2a237c4c027f9a2cba51` | 同 blob |
| `tests/cases/14_ui_eof_closure.sh` | `01473bd78b587d702ca9ab437af75e46ffa0d960` | **旧版**（无 7b） |

⇒ **可平移的换法**：把锚点换成 Chief 分支上可达的 tip（登记 95 条那棵），并把「台架侧 97 条」与「树内 95 条」分别写明。

### 3.2 第 ⑥ 样：条数三方对账在这批上也不成立

| 口径 | 条数 |
|---|---|
| `--list` 现场条数（台架侧 = 阿测装配树） | 97 |
| 汇总行 N | 97 |
| **冻结点树内** `tests/run_tests.sh` 登记表（`ddfb492`） | **95** |

⇒ **三方不相等 ⇒ 按 §0.4 第 ⑥ 样「任一不等 ⇒ 不得引用」**。

⇒ **根因不是条数错，是「跑的台架」与「树里的台架」是两份**（第 ⑦ 样的存在理由）：
**台架侧在途 97 条（T115/T116 未进树） vs 冻结点树内 95 条**。这不是缺陷，是口径问题；**引用时必须两处分别写**。

### 3.3 若要让它变成可引用，需同时满足三条

1. **锚点换成可达树**（如 Chief 分支 tip），或先把 T115/T116 落进树再以该树为锚；

## 六、★ 本机越界残留：归属判定（台架缺口，不是产品缺陷）

### 6.1 残留本体

| 项 | 实测 |
|---|---|
| 路径 | `C:/Users/liwend/AppData/Local/hermes/git/etc/realm/health/health_check.sh` |
| 字节 / 行数 | 6720 字节 / 187 行 |
| mtime | **2026-10-24 11:26:47** ⇒ **本轮 97 条跑批没有再写它**（阿测的这条知会属实） |
| 内容特征 | 头部写死 `HEALTH_DIR="/etc/realm/health"`、`RULES_DIR="/etc/realm/rules"`、`LOCK_FILE="/var/lock/realm-health-check.lock"` |

### 6.2 为什么会落在那里

`/etc/...` 在 **Windows + Git Bash（MSYS）** 下不是 Windows 的 `C:\etc`，而是**映射到 Git 安装根目录下的 `etc\`** ⇒ 这份文件实际落在 Git 安装目录里，**不是**任何产品的生产路径。

### 6.3 责任归属（逐环判定）

| 环 | 事实 | 判定 |
|---|---|---|
| 产品侧 | `lib/health.sh` 的健康脚本生成入口写的是**生产绝对路径** `/etc/realm/health/health_check.sh` | **生产上就该如此**（生产就装在 `/etc/realm/health/`）⇒ **不是缺陷** |
| 台架侧 | `tests/lib/sandbox.sh` 的 `sbx_redirect` 路径重定向表覆盖 `/etc/realm` 等目录，但**只对「被测产物引用该路径」生效**；**生成物落盘**这条写入路径没有被重定向 | **缺口在台架** |
| 台架侧 | `sbx_escape_scan` 只扫 `$SBX_RUN`（沙箱副本目录）⇒ **扫不到「写到 Git 安装目录里的 etc/」这一类** | **扫描盲区**（与阿测判断一致） |

⇒ **结论**：
1. 这**不是产品缺陷**，不需要改 `lib/`；
2. 但它暴露了台架的**两个缺口**：① 生成物落盘路径没被重定向；② 越界扫描只扫沙箱副本，扫不到沙箱外。
3. **建议补的台架项（交阿测/Chief，本轮不由小编动手）**：
   - 跑批**前后**各扫一次「Git 安装根目录 `etc/` + `/var/lib` + `/var/lock`」的落地文件并比对 ⇒ 把「越界写入」变成可检项；
   - 或给产品侧加一个**可覆盖的输出根目录**（如 `REALM_ETC_DIR`），让沙箱能把它指向沙箱内 —— 这一项**要动 `lib/health.sh`**，属产品侧改动，**须 Chief 拍板**，且要确认不改变生产语义。
4. **残留文件本身**在 Git 安装目录内，属本机环境文件 ⇒ **是否清理由用户定**，本轮**未删**（避免动 Git 安装目录里的东西）。
